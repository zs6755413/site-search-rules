# site-search-rules

> 一个内容站的站内搜索，没有 Elasticsearch、没有 Algolia、没有向量库、没有 embedding。只有一份 JSON 和一组打分规则。这里把整套规则摊开，附一个能直接跑的 demo。

这个仓库来自 [Kan112 AI 网址导航](https://www.kan112.com/) 的站内搜索实现——那边收录一千多个站点与五百多款 AI 工具，搜索要同时出站点、工具、问答、文章四类结果，但预算和技术栈都不允许上一个检索服务。

零依赖。同一份 `lib/` 代码既跑在 Node 里（命令行、服务端），也跑在浏览器里（静态页面直接加载），没有构建步骤。

浏览器演示就是仓库根目录的 `index.html`，通过 GitHub Pages 直接打开就能用，不需要任何后端。

## 问题在哪

小站的搜索有三条路，每条都有代价：

| 方案 | 代价 |
|---|---|
| 上 Elasticsearch / Meilisearch | 多一个要维护的服务，内存和磁盘都不是小站能随手给的 |
| 用 Algolia 这类托管搜索 | 按记录数和请求数计费，中文分词还要额外处理 |
| 数据库 `LIKE '%关键词%'` | 中文分词、排序、多字段权重全都做不了，结果不可用 |

第四条路很少有人认真做：**把数据摊在内存里，用规则打分。** 数据量在一万条以内时，这条路的效果和运维成本都不差。

这个仓库就是这条路的完整实现。

## 三个核心机制

### 1. 分词：不上词典，用 bigram

中文不切词，直接按两字切（bigram），单字查询时用单字兜底。

「站内搜索」切成 `站内` / `内搜` / `搜索`，短查询时整串也进词表。代价是噪声变多，收益是不用维护词典、不依赖任何分词库。噪声用字段权重压回去。

英文和数字按 `[a-z0-9]` 连续片段切，统一转小写。停用词表只有四十来个，包括「的」「怎么」「哪些」和 `vs`。

### 2. 打分：字段权重 × 覆盖率

一条结果得分由三部分构成：

```text
基础分 = 标题精确等于查询      100
       + 标题包含整串查询       55
       + 每个词命中标题         18
       + 每个词命中标签         12
       + 每个词命中摘要          7

覆盖率系数 = 0.55 + 0.45 × (命中的词数 / 总词数)
热度微调   = log10(热度 + 1) × 2

最终分 = 基础分 × 覆盖率系数 × 类型权重 + 热度微调
```

**覆盖率系数是这里最关键的一项。** 没有它，一个只命中「豆包」的长文档会盖过同时命中「豆包」和「DeepSeek」的短条目。乘上系数之后，命中词更全的结果自然排前面。

类型权重用来表达「同一份查询下，我更愿意先给用户看什么」：AI 工具 1.0、站点 0.92、实用工具 0.86、问答 0.8、文章 0.72。

### 3. 对比意图：先分词再匹配实体，而不是先检索再猜

用户输入 `豆包 vs deepseek`，期望的不是一堆包含这两个词的条目，而是一张「查看完整对比」的卡片。

判断逻辑刻意做得很保守：

1. 按分隔符优先级切分：先试带空格的 ` vs `，再试无空格的 `vs`（要求它前面不是英文字母，避免把 `eavesdrop` 这类词拆开），最后才是 `对比`、`和`、`与`、`跟`
2. 两段都要能在实体表里**命中且唯一**——精确相等优先，退一步才用「包含」
3. 两段必须落到两个**不同**的实体
4. 这两个实体之间**必须存在已配对的对比页**

四条全过才出卡片。任何一条不满足就不显示。

**为什么不猜。** 「豆包和电脑哪个好」这种句子，硬猜就会猜错，猜错比不显示更伤。规则的价值不在于覆盖面，在于错的时候不出现。

同时，命中的两个实体在各自分组里会获得 +40 加成，确保它们排在分组顶部——卡片和结果指向同一批条目，用户不会觉得两处东西对不上。

### 4. 降级：无结果不等于死路

查不到结果时，页面不是显示「没有找到」，而是给两样东西：

- **相近分类**：把查询的词和分类关键词表做双向包含匹配，取前三个
- **热门条目**：按热度取前五条

一次失败的检索，可以被引导成一次有效的浏览。

## 跑起来

```bash
# 命令行查一条
node bin/cli.js "豆包 vs deepseek"

# 带标签筛选（多个条件为「同时满足」）
node bin/cli.js "编程" --flags free,nologin

# 搜索联想
node bin/cli.js --suggest "豆"

# 规则自检，15 条用例
node bin/cli.js --check

# 起本地服务，浏览器打开 http://localhost:3000
node server.js
```

## 接口

起 `node server.js` 之后有三个 JSON 接口，也可以直接把 `lib/` 引到自己的项目里：

```bash
curl "http://localhost:3000/api/search?q=豆包&flags=free"
curl "http://localhost:3000/api/suggest?q=豆"
curl "http://localhost:3000/api/stats"
```

`flags` 支持 `free`（有免费额度）、`trial`（可试用）、`nologin`（免登录），逗号分隔表示同时满足。

返回结构：

```json
{
  "query": "豆包 vs deepseek",
  "terms": ["deepseek", "豆包"],
  "took": 1,
  "total": 7,
  "vs": { "title": "豆包 vs DeepSeek", "desc": "...", "slug": "豆包-vs-DeepSeek" },
  "groups": [
    { "type": "aiTool", "label": "AI 工具", "total": 2, "items": [ { "title": "豆包", "score": 59.9, "hl": {} } ] }
  ],
  "fallback": null
}
```

## 自检

`node bin/cli.js --check` 会跑 15 条用例，覆盖分批、对比意图、筛选、降级四块：

```text
规则自检
  PASS  单实体命中，多类聚合  (q="豆包")
  PASS  vs 卡片：空格分隔  (q="豆包 vs deepseek")
  PASS  vs 卡片：无空格  (q="豆包vsdeepseek")
  PASS  vs 卡片：中文对比  (q="豆包对比deepseek")
  PASS  vs 卡片：顺序无关  (q="deepseek vs 豆包")
  PASS  单实体不出 vs 卡片  (q="豆包")
  PASS  未配对实体不出卡片  (q="豆包 vs Cursor")
  PASS  非实体词不出卡片  (q="豆包和电脑")
  ...
  15/15 通过
```

最后三条是「不该出卡片的时候不出」的反向用例。**这类用例比正向用例重要**——过度触发是这类规则最常见的失败方式。

## 拆成系列的话，可以这么写

这个仓库的内容按难度拆成四篇，每篇对应代码里的一个文件：

| 篇 | 主题 | 对应代码 |
|---|---|---|
| 一 | 分词与匹配：不上词典，bigram 能撑多远 | `lib/tokenize.js` |
| 二 | 打分与分组：字段权重、覆盖率系数怎么定 | `lib/search.js` 的 `scoreDoc` |
| 三 | 对比意图：A vs B 怎么判断，什么时候该放弃 | `lib/search.js` 的 `detectVs` |
| 四 | 降级：无结果页怎么变成一次有效浏览 | `lib/search.js` 的 `fallbackFor` |

## 边界

**数据量。** 一万条以内很舒服，五万条开始要注意首屏加载（JSON 体积）和全表打分的时间。再往上就该考虑真正的索引结构了。

**它不做的事。** 不做拼写纠错、不做同义词扩展、不做拼音首字母、不记录点击反馈。这些都能加，但每加一项都会多一类误判，先不做。

**中文分词的固有代价。** bigram 会出现「内搜」这种无意义片段，靠字段权重和覆盖率压住。如果你的内容里同义表述很多（「AI 绘画」和「文生图」），单靠字符串匹配会漏，需要一张同义词表补上。

**权重是拍出来的，不是算出来的。** 表里的 100 / 55 / 18 / 12 / 7 来自实际调参，没有理论依据。换一份语料就要重新看一遍排序结果。这一点在 README 里说清楚，比假装它是科学好。
